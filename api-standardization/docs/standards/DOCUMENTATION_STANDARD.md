## 1. Docstrings Python

| ID | Правило | Уровень |
|---|---|---|
| DOC-PY-01 | Docstring обязателен для каждого публичного модуля, класса, метода сервисного слоя, функции роутера и нетривиальной функции. Публичным считается имя без ведущего подчёркивания | ОБЯЗАТЕЛЬНО |
| DOC-PY-02 | Docstrings оформляются по PEP 257: тройные двойные кавычки, первая строка — краткое назначение, законченное предложение с точкой | ОБЯЗАТЕЛЬНО |
| DOC-PY-03 | Многострочный docstring использует стиль Google: секции `Args:`, `Returns:`, `Yields:`, `Raises:`, `Attributes:`, `Example:` | ОБЯЗАТЕЛЬНО |
| DOC-PY-04 | Секция `Raises:` перечисляет исключения, видимые вызывающему коду, в том числе `APIProblem` с условием возникновения | ОБЯЗАТЕЛЬНО |
| DOC-PY-05 | Docstring не дублирует сигнатуру и очевидный код; описываются назначение, ограничения, побочные эффекты (запись в журнал аудита, commit) | ОБЯЗАТЕЛЬНО |
| DOC-PY-06 | Язык docstrings — русский; идентификаторы, имена полей и значения enum — в исходном написании | ОБЯЗАТЕЛЬНО |
| DOC-PY-07 | Docstring функции роутера является `description` операции в OpenAPI, поэтому в нём указывается требуемая роль или уровень доступа | ОБЯЗАТЕЛЬНО |
| DOC-PY-08 | Модули, реализующие правило стандарта, ссылаются на его идентификатор (`STD-ERR-01`, `SEC-RL-01`) | РЕКОМЕНДУЕТСЯ |
| DOC-PY-09 | Пустые `__init__.py` пакетов docstring не требуют | ДОПУСКАЕТСЯ |

Пример:

```python
def get_project(self, project_id: int, user: User) -> Project:
    """Вернуть проект, доступный пользователю.

    Args:
        project_id: Идентификатор проекта.
        user: Аутентифицированный пользователь.

    Returns:
        Проект, к которому у пользователя есть доступ.

    Raises:
        APIProblem: Если проект не существует или недоступен (404).
    """
```

## 2. OpenAPI

| ID | Правило | Уровень |
|---|---|---|
| DOC-API-01 | Требования к описанию операций установлены в разделе 7 `API_STANDARD.md` (STD-DOC-01…11) | ОБЯЗАТЕЛЬНО |
| DOC-API-02 | У каждого поля схемы запроса и ответа есть `description`; у ключевых схем — `examples` | ОБЯЗАТЕЛЬНО |
| DOC-API-03 | Каждый тег имеет описание в `openapi_tags` | ОБЯЗАТЕЛЬНО |
| DOC-API-04 | Фактическая схема экспортируется командой `python -m scripts.export_openapi` в `docs/openapi/openapi.json` и коммитится вместе с изменением контракта. Расхождение файла и приложения обнаруживает тест `test_exported_schema_matches_application` | ОБЯЗАТЕЛЬНО |
| DOC-API-05 | Swagger UI (`/docs`) и ReDoc (`/redoc`) должны позволять использовать API без чтения исходного кода: в общем описании указаны базовый путь, способ получения токена, роли, формат ошибок и пагинации | ОБЯЗАТЕЛЬНО |

## 3. Sphinx

| ID | Правило | Уровень |
|---|---|---|
| DOC-SPX-01 | Исходники документации — в `docs/source/`; результат сборки `docs/build/` в репозиторий не коммитится | ОБЯЗАТЕЛЬНО |
| DOC-SPX-02 | `conf.py` подключает расширения `sphinx.ext.autodoc`, `sphinx.ext.napoleon` (`napoleon_google_docstring = True`), `sphinx.ext.viewcode` | ОБЯЗАТЕЛЬНО |
| DOC-SPX-03 | Обязательные разделы: `overview`, `api_contract`, `security`, `versioning`, `api_reference` | ОБЯЗАТЕЛЬНО |
| DOC-SPX-04 | `api_reference.rst` строится через autodoc по всем публичным модулям `app/` | ОБЯЗАТЕЛЬНО |
| DOC-SPX-05 | Сборка `sphinx-build -b html docs/source docs/build/html` проходит без ошибок импорта модулей | ОБЯЗАТЕЛЬНО |
| DOC-SPX-06 | Сборка с флагом `-W` (предупреждения как ошибки) | РЕКОМЕНДУЕТСЯ |
