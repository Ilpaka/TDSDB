# Урок 1. Каталог серверов в аренду

Предметная область — хостинг-провайдер. Коллекция `hosting.servers` хранит карточки
товаров: выделенные серверы и VPS, которые сдаются в аренду. Это то, что видит клиент
в каталоге и по чему фильтрует: локация, железо, цена, наличие.

## Состав

| Файл | Что внутри |
|---|---|
| `seed.json` | 5 документов коллекции в Extended JSON (массив) |
| `queries.md` | 5 рабочих фильтров + 1 намеренно сломанный, с ожидаемыми счётчиками |
| `screenshot.png` | Коллекция в Compass со счётчиком документов |
| `../MongoDB/` | docker-compose, Makefile и init-скрипт, который заливает `seed.json` при первом старте |

## Как поднять на чистой машине

Нужны Docker и `make`.

```bash
cd MongoDB
make up
```

Образ `mongo:7` при первом старте с пустым volume выполняет скрипты из
`docker-entrypoint-initdb.d` — там лежит `init/01-seed.sh`, который через `mongoimport`
заливает `lesson-01/seed.json` в базу `hosting`, коллекцию `servers`. Руками ничего
импортировать не нужно.

Подключение в Compass:

```
mongodb://root:root@localhost:27017/?authSource=admin
```

Открыть `hosting` → `servers`. Счётчик должен показать **5** документов.

Если нужно накатить данные заново (например, после правок в `seed.json`):

```bash
make reseed    # = down -v + up
```

Остановить: `make down` (данные остаются в volume), `make clean` — снести вместе с данными.

Если Docker неудобен, файл импортируется и руками: в Compass создать базу `hosting`
с коллекцией `servers`, затем **Add Data → Import JSON or CSV file → seed.json**.
Числа в `queries.md` от способа импорта не зависят.

## Как устроен документ

```
sku            — артикул, уникальный идентификатор карточки в каталоге
name, type     — название и тип: dedicated | vps
status, stock  — доступность и сколько единиц осталось
location       — { dc, city, country } — где физически стоит
hardware       — { cpu: {model, cores, threads}, ram_gb, storage: [ {type, size_gb, count} ], bandwidth_mbps }
price          — { monthly_rub, setup_rub?, currency }
tags           — массив строк для фасетного поиска
created_at     — дата добавления карточки
```

Форма документов намеренно не одинаковая — так оно и бывает в живом каталоге:

- `DED-SPB-002` — единственный с полем `hardware.gpu`.
- `DED-MSK-003` — есть `discount` (акция), у остальных такого поля нет.
- `VPS-MSK-101`, `VPS-AMS-201` — есть `virtualization`, но нет `price.setup_rub`:
  у VPS нет платы за подключение, и вместо `setup_rub: 0` поле просто отсутствует.
- `VPS-AMS-201` — без `tags`: карточку завели, а теги ещё не проставили.

Именно из-за этих различий в `queries.md` появляется запрос с `$exists`.

## Абзац о цене дублирования

Самое дорогое дублирование здесь — `location`. В каждой карточке лежит целиком
`{ dc, city, country }`, и на пяти документах это два раза `SPB-1 / Санкт-Петербург`,
два раза `MSK-2 / Москва` и один `AMS-1`. Пока карточек пять, это ничего не стоит.
Но у реального провайдера в одной площадке сотни позиций, и когда площадку `MSK-2`
переезжают из Москвы в область или переименовывают в `MSK-3`, придётся сделать
`updateMany` по всем документам с этим `dc`, причём атомарно этого не сделать: между
началом и концом обновления клиент увидит часть каталога со старым городом, часть — с
новым. Плюс любое расхождение (`"Москва"` vs `"Москва "` с пробелом) сразу ломает фильтр
по городу: документ просто выпадает из выдачи, и никто не узнает.

Второе место — `hardware.cpu.model`. Одна и та же модель процессора повторяется
строкой в каждой карточке. Ошибся в написании один раз — и фильтр «все серверы на
5950X» этого сервера не покажет. Но здесь я осознанно оставляю дублирование: карточка
товара должна быть самодостаточной, чтобы отдавать её в одну выборку без `$lookup`.
Процессор у конкретного сервера не меняется, а вот `location` — реальный кандидат
на вынос в отдельную коллекцию `datacenters` с хранением в карточке только `dc`-кода.
Цена такого решения — лишний запрос при отдаче каталога, и это дешевле, чем массовое
обновление при переезде площадки.
