## 2. Детализация несоответствий

Для каждого FAIL: где найдено, в чём проблема, какой риск, что планируется изменить.

### A-01. Единая версия публичного API

- **Где:** `app/main.py:70-75`, все `APIRouter` в `app/routers/`.
- **Проблема:** публичный контракт не версионирован. Любое несовместимое изменение
  ломает клиентов без возможности параллельного существования версий.
- **Риск:** невозможность эволюции API; отсутствие процедуры deprecation;
  версия приложения (`1.0.0`) ошибочно воспринимается как версия контракта.
- **Действие:** ввести общий роутер `/api/v1`, оставив вне версии `/health`,
  `/docs`, `/redoc`, `/openapi.json`. Зафиксировать различие версии приложения
  и версии контракта в `docs/standards/API_STANDARD.md`.

### A-02. Единообразие URI

- **Где:** `projects.py:15` vs `projects.py:23`; `users.py:14`; `auditlog.py:17`;
  `access.py:12`; `documents.py:56,66`.
- **Проблема:** одновременно существуют `/projects` и `/projects/`, что порождает
  307-редиректы и два адреса для одного ресурса. В URI присутствуют глаголы
  (`grant`, `publish`, `archive`, `restore`).
- **Риск:** неоднозначность контракта, потеря заголовка `Authorization` частью
  HTTP-клиентов при редиректе, невозможность автоматической проверки стиля.
- **Действие:** принять единый стиль без завершающего слэша; заменить глагольные
  URI на операции над ресурсом или подресурсом состояния.

### A-03. HTTP-методы

- **Где:** `documents.py:56,66,88`; `access.py:12`.
- **Проблема:** изменение атрибута `status` документа моделируется как отдельное
  действие (`POST /publish`), а не как изменение состояния ресурса.
  Выдача доступа и его отзыв реализованы асимметрично.
- **Риск:** неограниченный рост числа глагольных операций, невозможность
  предсказать контракт по ресурсной модели.
- **Действие:** привести операции изменения состояния к `PATCH` над ресурсом
  либо к явно документированному подресурсу; выдачу доступа — к `PUT/POST`
  над коллекцией `access` без глагола.

### A-04. Status codes

- **Где:** все роутеры.
- **Проблема:** коды успеха заданы выборочно, коды ошибок не объявлены.
  Потребитель API не может узнать из контракта, какие ошибки возможны.
- **Риск:** клиентская обработка ошибок пишется методом подбора; регрессии в
  кодах ответов не обнаруживаются.
- **Действие:** задать `status_code` каждой операции и объявить `responses`
  для всех ожидаемых ошибок согласно таблице стандарта.

### A-05. Формат ошибок

- **Где:** `security.py:70,95,113`; `auth.py:22`; `users.py:20`; сервисный слой.
- **Проблема:** в API сосуществуют минимум два формата ошибок — `{"detail": "строка"}`
  и `{"detail": [объекты]}` для 422. Стандарт RFC 9457 не применён.
- **Риск:** клиент вынужден разбирать разные структуры для одного класса ошибок;
  сообщения об ошибках не машиночитаемы.
- **Действие:** внедрить общие exception handlers, возвращающие Problem Details
  (`type`, `title`, `status`, `detail`, `instance`), с дополнительным полем
  `errors` для ошибок валидации.

### A-06. Полнота OpenAPI

- **Где:** все операции.
- **Проблема:** схема содержит пути и модели, но не содержит человекочитаемого
  описания операций, стабильных `operationId` и описания ошибок.
- **Риск:** документация непригодна для использования API без чтения исходного
  кода; генераторы клиентов создают нестабильные имена методов.
- **Действие:** дополнить каждую операцию `tags`, `summary`, `description`,
  `operation_id`, `response_model`, `status_code`, `response_description`,
  `responses`, описанием параметров и примерами.

### A-07. Аутентификация и авторизация в контракте

- **Где:** `security.py:107-111`, `auditlog.py:26`, `users.py:17-22`, `auth.py:15-19`.
- **Проблема:** `require_admin` возвращает `bool` вместо возбуждения `HTTPException`.
  В `users.py` и `auth.py` результат проверяется вручную, в `auditlog.py` — **нет**,
  поэтому журнал аудита доступен любому аутентифицированному пользователю.
  Кроме того, `False` подставляется в аргумент, аннотированный как `User`.
- **Риск:** нарушение разграничения доступа (OWASP API5 Broken Function Level
  Authorization); раскрытие журнала действий всех пользователей.
- **Действие:** переписать проверку роли как зависимость, возбуждающую 403;
  покрыть тестом; отразить требования авторизации в описании операций.

### A-08. Production-defaults

- **Где:** `app/core/config.py:8-18`.
- **Проблема:** секрет подписи JWT имеет рабочее значение по умолчанию.
  При отсутствии `.env` приложение стартует и выпускает валидные токены,
  подделываемые любым, кто видел исходный код.
- **Риск:** полная компрометация аутентификации (OWASP API2, API8).
- **Действие:** сделать `JWT_SECRET` обязательным без значения по умолчанию,
  добавить проверку при старте, задокументировать в `SECURITY_STANDARD.md`.

### A-09. CORS

- **Где:** `app/main.py:45-51`.
- **Проблема:** wildcard-origin в сочетании с `allow_credentials=True`.
  Конфигурация одинакова для всех сред.
- **Риск:** межсайтовые запросы с учётными данными; несоответствие требованиям
  OWASP API8 Security Misconfiguration.
- **Действие:** вынести список разрешённых origin в настройки среды,
  запретить wildcard при `allow_credentials=True`.

### A-10. Документация

- **Где:** корень репозитория, `docs/`.
- **Проблема:** `README.md` пуст; отсутствуют политика безопасности, история
  изменений, внутренние стандарты, Sphinx и экспортированный контракт.
- **Риск:** невозможность самостоятельного запуска и сопровождения проекта;
  отсутствие критериев для оценки соответствия.
- **Действие:** подготовить `README.md`, `SECURITY.md`, `CHANGELOG.md`,
  три документа стандартов, Sphinx-документацию и `docs/openapi/openapi.json`.

## 4. Вывод по baseline

На момент commit `ccc390a` API **не соответствует** ни одному из десяти
установленных критериев. Основные системные причины:

1. Публичный контракт не версионирован и не отделён от реализации.
2. OpenAPI-схема генерируется автоматически и не рассматривается как контракт.
3. Модель ошибок отсутствует как проектное решение.
4. Разграничение доступа реализовано непоследовательно и содержит рабочий дефект.
5. Конфигурация безопасности не зависит от среды исполнения.

Данный документ фиксирует исходное состояние объекта оценки и далее не изменяется.
Результаты исправлений отражаются в `docs/audit/CERTIFICATION_REPORT.md`.
