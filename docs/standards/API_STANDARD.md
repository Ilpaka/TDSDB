# API STANDARD v1 — Document Center API

Внутренний стандарт публичного REST API.

| Параметр | Значение |
|---|---|
| Идентификатор документа | `API_STANDARD` |
| Версия стандарта | 1.0.0 |
| Статус | Действующий |
| Дата введения | 2026-09-09 |
| Область применения | Публичный HTTP-контракт Document Center API |
| Владелец | Команда разработки Document Center API |

## Назначение

Документ устанавливает обязательные правила проектирования публичного HTTP-API.
Стандарт разработан **до** внесения исправлений в код и применяется как критерий
последующей оценки соответствия. Реализация проверяется на соответствие
стандарту, а не наоборот: расхождение между кодом и настоящим документом
трактуется как несоответствие кода.

## Термины и уровни требований

**ОБЯЗАТЕЛЬНО** — требование, невыполнение которого является несоответствием.
**РЕКОМЕНДУЕТСЯ** — отклонение допускается при письменном обосновании
в `CERTIFICATION_REPORT.md`.
**ДОПУСКАЕТСЯ** — разрешённый, но не единственный вариант.

Каждое правило имеет идентификатор вида `STD-XXX-NN`. Проверки соответствия
в `tests/` и записи в `CERTIFICATION_REPORT.md` ссылаются на эти идентификаторы.

## 1. Версионирование

| ID | Правило | Уровень |
|---|---|---|
| STD-VER-01 | Все бизнес-операции размещаются под префиксом `/api/v1` | ОБЯЗАТЕЛЬНО |
| STD-VER-02 | Вне версии остаются только `/health`, `/docs`, `/redoc`, `/openapi.json` и корневой `/` | ОБЯЗАТЕЛЬНО |
| STD-VER-03 | Версия публичного контракта (`v1`) и версия приложения (`1.2.0`, SemVer) — независимые понятия и не отождествляются | ОБЯЗАТЕЛЬНО |
| STD-VER-04 | Несовместимое изменение контракта требует новой major-версии API либо формальной процедуры deprecation | ОБЯЗАТЕЛЬНО |
| STD-VER-05 | Устаревающая операция помечается `deprecated=True` и документируется до момента удаления | ОБЯЗАТЕЛЬНО |
| STD-VER-06 | Срок жизни deprecated-операции — не менее одной minor-версии приложения | РЕКОМЕНДУЕТСЯ |

**Несовместимыми считаются:** удаление или переименование операции, поля или
enum-значения; изменение типа поля; добавление обязательного поля в запрос;
изменение кода успешного ответа; изменение структуры тела ошибки; сужение
диапазона допустимых значений параметра.

**Совместимыми считаются:** добавление операции; добавление необязательного
поля запроса; добавление поля в ответ; добавление нового кода ошибки для
ранее недокументированного условия.

## 2. URI

| ID | Правило | Уровень |
|---|---|---|
| STD-URI-01 | Только нижний регистр; слова разделяются дефисом | ОБЯЗАТЕЛЬНО |
| STD-URI-02 | Ресурс именуется существительным во множественном числе: `/projects`, `/documents`, `/users` | ОБЯЗАТЕЛЬНО |
| STD-URI-03 | Глаголы в URI запрещены; действие выражается HTTP-методом | ОБЯЗАТЕЛЬНО |
| STD-URI-04 | Завершающий слэш не используется: канонический вид — `/api/v1/projects` | ОБЯЗАТЕЛЬНО |
| STD-URI-05 | Идентификатор оформляется как `{resource_id}` в snake_case: `/projects/{project_id}` | ОБЯЗАТЕЛЬНО |
| STD-URI-06 | Вложенность не превышает двух уровней ресурсов: `/projects/{project_id}/documents` | ОБЯЗАТЕЛЬНО |
| STD-URI-07 | Ресурс имеет один канонический путь; альтернативная адресация того же ресурса запрещена | ОБЯЗАТЕЛЬНО |
| STD-URI-08 | Подчинённая сущность, имеющая собственный идентификатор, адресуется плоско после создания во вложенном контексте | ДОПУСКАЕТСЯ |

**Разрешение конфликта для документов.** Документ создаётся в контексте проекта
(`POST /api/v1/projects/{project_id}/documents`), поскольку проект определяет
права доступа. После создания документ имеет собственный идентификатор и
адресуется канонически как `/api/v1/documents/{document_id}` (STD-URI-08).
Коллекция `/api/v1/projects/{project_id}/documents` доступна только для чтения.

**Замена глагольных операций.** Изменение состояния ресурса выполняется через
`PATCH` над полем состояния, а не через отдельную операцию-действие:

| Было | Стало |
|---|---|
| `POST /documents/{id}/publish` | `PATCH /api/v1/documents/{id}` с телом `{"status": "published"}` |
| `POST /documents/{id}/archive` | `PATCH /api/v1/documents/{id}` с телом `{"status": "archived"}` |
| `POST /projects/{id}/access/grant` | `PUT /api/v1/projects/{id}/access/{user_id}` |
| `POST /documents/{id}/versions/{v}/restore` | `POST /api/v1/documents/{id}/versions` с телом `{"restore_from": v}` |

Восстановление версии сохранено как `POST` над коллекцией версий: операция
создаёт новую версию, а не изменяет существующую, и по семантике RFC 9110
является созданием ресурса.

## 3. HTTP-методы и коды состояния

| ID | Правило | Уровень |
|---|---|---|
| STD-HTTP-01 | Соответствие «операция — метод — код» определяется таблицей ниже | ОБЯЗАТЕЛЬНО |
| STD-HTTP-02 | Код успешного ответа задаётся явно (`status_code=`) для каждой операции | ОБЯЗАТЕЛЬНО |
| STD-HTTP-03 | `GET`, `PUT`, `DELETE` идемпотентны; `GET` не изменяет состояние | ОБЯЗАТЕЛЬНО |
| STD-HTTP-04 | Ответ `204` не содержит тела | ОБЯЗАТЕЛЬНО |
| STD-HTTP-05 | Все ожидаемые коды ошибок объявляются в `responses` операции | ОБЯЗАТЕЛЬНО |
| STD-HTTP-06 | `Content-Type` тела запроса и ответа — `application/json`; для ошибок — `application/problem+json` | ОБЯЗАТЕЛЬНО |

### 3.1. Таблица операций

| Операция | Метод | Код успеха | Тело ответа |
|---|---|---|---|
| Получить ресурс или коллекцию | `GET` | 200 | Ресурс / конверт коллекции |
| Создать ресурс | `POST` | 201 | Созданный ресурс |
| Создать или заменить по известному ключу | `PUT` | 200 (обновление) / 201 (создание) | Ресурс |
| Частично изменить ресурс | `PATCH` | 200 | Изменённый ресурс |
| Удалить ресурс | `DELETE` | 204 | Отсутствует |

### 3.2. Таблица кодов ошибок

| Код | Условие применения |
|---|---|
| 400 | Запрос синтаксически корректен, но нарушает бизнес-правило, не сводимое к валидации схемы |
| 401 | Аутентификация отсутствует, токен недействителен или истёк |
| 403 | Аутентификация выполнена, но прав на операцию или объект недостаточно |
| 404 | Ресурс не существует либо недоступен текущему пользователю |
| 409 | Конфликт состояния: нарушение уникальности, недопустимый переход состояния |
| 422 | Тело или параметры запроса не соответствуют схеме |
| 429 | Превышено ресурсное ограничение частоты запросов |

**Разграничение 403 и 404.** Если факт существования ресурса сам по себе не
является конфиденциальным, возвращается `403`. Если раскрытие существования
ресурса даёт непривилегированному пользователю информацию о чужих объектах,
возвращается `404` (STD-SEC-07).

**Разграничение 400, 409 и 422.** Несоответствие схеме — `422`. Нарушение
уникальности (занятый email, повторная выдача доступа) — `409`. Недопустимый
переход состояния (публикация архивированного документа) — `409`.
Код `400` применяется только к прочим нарушениям бизнес-правил.

## 4. Формат данных

| ID | Правило | Уровень |
|---|---|---|
| STD-DATA-01 | Имена полей JSON — `snake_case` | ОБЯЗАТЕЛЬНО |
| STD-DATA-02 | Один и тот же идентификатор имеет один тип во всех операциях | ОБЯЗАТЕЛЬНО |
| STD-DATA-03 | Пароли, хэши, секреты и внутренние технические поля не входят в `response_model` | ОБЯЗАТЕЛЬНО |
| STD-DATA-04 | Дата и время — RFC 3339 в UTC с суффиксом `Z`: `2026-09-09T08:15:30Z` | ОБЯЗАТЕЛЬНО |
| STD-DATA-05 | Перечислимые значения оформляются как `enum` в нижнем регистре и документируются в схеме | ОБЯЗАТЕЛЬНО |
| STD-DATA-06 | Обязательность поля определяется схемой; `null` и отсутствие поля не эквивалентны | ОБЯЗАТЕЛЬНО |
| STD-DATA-07 | Каждая операция имеет `response_model`; возврат необъявленных структур запрещён | ОБЯЗАТЕЛЬНО |
| STD-DATA-08 | Для `PATCH` неуказанное поле означает «не изменять», явный `null` — «очистить» | ОБЯЗАТЕЛЬНО |

## 5. Коллекции: пагинация, фильтрация, сортировка

| ID | Правило | Уровень |
|---|---|---|
| STD-COL-01 | Параметры пагинации — `offset` и `limit`; имя `skip` не используется | ОБЯЗАТЕЛЬНО |
| STD-COL-02 | `offset >= 0`, `limit >= 1`, максимальный `limit` = 100 для всех коллекций без исключений | ОБЯЗАТЕЛЬНО |
| STD-COL-03 | Значение `limit` по умолчанию — 20 | ОБЯЗАТЕЛЬНО |
| STD-COL-04 | Превышение максимума `limit` отклоняется кодом 422, а не молча усекается | ОБЯЗАТЕЛЬНО |
| STD-COL-05 | Любая коллекция поддерживает пагинацию, включая вложенные | ОБЯЗАТЕЛЬНО |
| STD-COL-06 | Ответ-коллекция возвращается в конверте `items`, `total`, `offset`, `limit` | ОБЯЗАТЕЛЬНО |
| STD-COL-07 | Ограничения `ge` / `le` / `min_length` / `max_length` объявляются в схеме и попадают в OpenAPI | ОБЯЗАТЕЛЬНО |
| STD-COL-08 | Сортировка задаётся параметром `sort` в форме `field` / `-field`; допустимые поля перечисляются в описании | РЕКОМЕНДУЕТСЯ |

```json
{
  "items": [ { "id": 1, "title": "Смета" } ],
  "total": 137,
  "offset": 0,
  "limit": 20
}
```

Переход на конверт коллекции (STD-COL-06) является несовместимым изменением
контракта и подлежит обязательной фиксации в `CHANGELOG.md` как breaking change.

## 6. Модель ошибок

| ID | Правило | Уровень |
|---|---|---|
| STD-ERR-01 | Тело любой ошибки соответствует RFC 9457 Problem Details | ОБЯЗАТЕЛЬНО |
| STD-ERR-02 | Обязательные члены: `type`, `title`, `status`, `detail`, `instance` | ОБЯЗАТЕЛЬНО |
| STD-ERR-03 | `type` — стабильный URI вида `https://docs.local/problems/{slug}`; изменение `type` считается несовместимым | ОБЯЗАТЕЛЬНО |
| STD-ERR-04 | `title` не зависит от конкретного экземпляра ошибки; переменная часть помещается в `detail` | ОБЯЗАТЕЛЬНО |
| STD-ERR-05 | Ошибка валидации дополняется членом `errors` — массивом `{field, message}` | ОБЯЗАТЕЛЬНО |
| STD-ERR-06 | Тело ошибки не содержит stack trace, SQL-текста, секретов, внутренних путей и имён таблиц | ОБЯЗАТЕЛЬНО |
| STD-ERR-07 | Один класс ошибки имеет одинаковую структуру во всех операциях | ОБЯЗАТЕЛЬНО |
| STD-ERR-08 | Ошибки формируются централизованными exception handlers, а не поштучно в роутерах | ОБЯЗАТЕЛЬНО |
| STD-ERR-09 | Ответ с ошибкой имеет `Content-Type: application/problem+json` | ОБЯЗАТЕЛЬНО |

{
  "type": "https://docs.local/problems/project-not-found",

## 7. Требования к описанию операции в OpenAPI

| ID | Правило | Уровень |
|---|---|---|
| STD-DOC-01 | Операция отнесена к содержательному `tag` из фиксированного перечня | ОБЯЗАТЕЛЬНО |
| STD-DOC-02 | Задан `summary` — одна строка в повелительном наклонении | ОБЯЗАТЕЛЬНО |
| STD-DOC-03 | Задано `description` либо содержательный docstring функции | ОБЯЗАТЕЛЬНО |
| STD-DOC-04 | Задан `operation_id` — уникальный, стабильный, в `snake_case` | ОБЯЗАТЕЛЬНО |
| STD-DOC-05 | Заданы `response_model` и `status_code` | ОБЯЗАТЕЛЬНО |
| STD-DOC-06 | Задано `response_description` | ОБЯЗАТЕЛЬНО |
| STD-DOC-07 | Объявлены `responses` для всех кодов из раздела 3.2, применимых к операции | ОБЯЗАТЕЛЬНО |
| STD-DOC-08 | Все path- и query-параметры имеют `description` и ограничения | ОБЯЗАТЕЛЬНО |
| STD-DOC-09 | Ключевые схемы содержат `examples` | ОБЯЗАТЕЛЬНО |
| STD-DOC-10 | Защищённые операции отражают требование Bearer в схеме безопасности | ОБЯЗАТЕЛЬНО |
| STD-DOC-11 | `operation_id` не изменяется при рефакторинге имени функции | ОБЯЗАТЕЛЬНО |

Перечень допустимых `tags`: `Authentication`, `Users`, `Projects`, `Access`,
`Documents`, `Audit`, `Health`.

```python
@router.get(
    "/{project_id}",
    response_model=ProjectRead,
    status_code=status.HTTP_200_OK,
    summary="Получить проект",
    response_description="Карточка проекта",
    operation_id="get_project",
    responses={
        401: {"model": ProblemDetails, "description": "Authentication required"},
        403: {"model": ProblemDetails, "description": "Access denied"},
        404: {"model": ProblemDetails, "description": "Project not found"},
    },
)
def get_project(...):
    """Return a project available to the current user."""
```

## 8. Безопасность контракта

Детальные требования установлены в `SECURITY_STANDARD.md`. Настоящий раздел
фиксирует то, что обязано быть выражено **в самом контракте**.

| ID | Правило | Уровень |
|---|---|---|
| STD-SEC-01 | Схема безопасности Bearer/JWT явно объявлена в `securitySchemes` | ОБЯЗАТЕЛЬНО |
| STD-SEC-02 | Каждая защищённая операция помечена требованием security | ОБЯЗАТЕЛЬНО |
| STD-SEC-03 | Публичные операции перечислены явно: `POST /api/v1/auth/login`, `GET /health`, `GET /` | ОБЯЗАТЕЛЬНО |
| STD-SEC-04 | Требуемая роль указана в `description` операции | ОБЯЗАТЕЛЬНО |
| STD-SEC-05 | Проверка роли реализуется зависимостью, возбуждающей 403, а не возвратом `bool` | ОБЯЗАТЕЛЬНО |
| STD-SEC-06 | Операции с `{id}` выполняют object-level authorization до возврата данных | ОБЯЗАТЕЛЬНО |
| STD-SEC-07 | Для чужих объектов возвращается `404`, если факт существования конфиденциален | ОБЯЗАТЕЛЬНО |
| STD-SEC-08 | Ответ `401` сопровождается заголовком `WWW-Authenticate: Bearer` | ОБЯЗАТЕЛЬНО |
| STD-SEC-09 | Решение о rate limiting документируется: внедрено либо обосновано отсутствие | ОБЯЗАТЕЛЬНО |

Роли: `admin`, `manager`, `worker`, `viewer`.
Уровни доступа к проекту: `viewer`, `editor`.

администратором через `POST /api/v1/users` (STD-URI-03, STD-SEC-04).

## 10. Порядок проверки соответствия

Соответствие подтверждается автоматически там, где это возможно.

| Группа правил | Способ проверки |
|---|---|
| STD-VER-01…02, STD-URI-04, STD-URI-07 | `tests/test_openapi_contract.py` — анализ `paths` в `openapi.json` |
| STD-DOC-01…09 | `tests/test_openapi_contract.py` — обход всех операций схемы |
| STD-HTTP-01…05, STD-COL-01…06 | `tests/test_http_contract.py` — вызовы через `TestClient` |
| STD-ERR-01…09 | `tests/test_http_contract.py` — проверка структуры тела ошибок |
| STD-SEC-01…09 | `tests/test_security_contract.py` |
| STD-VER-03…06, STD-SEC-09 | Ручная проверка, фиксируется в `CERTIFICATION_REPORT.md` |

Отклонение от любого правила уровня ОБЯЗАТЕЛЬНО без записи в разделе
«Остаточные несоответствия» итогового отчёта делает заключение
о соответствии недействительным.
