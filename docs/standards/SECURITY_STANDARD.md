Внутренний стандарт безопасности публичного REST API.

## Назначение

Стандарт устанавливает обязательные требования безопасности к реализации и
конфигурации API. Требования, которые должны быть выражены в самом
HTTP-контракте (схема Bearer, коды 401/403, заголовок `WWW-Authenticate`),
закреплены в разделе 8 `API_STANDARD.md`; настоящий документ детализирует
их реализацию.

Уровни требований (**ОБЯЗАТЕЛЬНО**, **РЕКОМЕНДУЕТСЯ**, **ДОПУСКАЕТСЯ**) трактуются
так же, как в `API_STANDARD.md`.

## 1. Аутентификация

| ID | Требование | Уровень |
|---|---|---|
| SEC-AUTH-01 | Аутентификация выполняется по схеме Bearer с токеном JWT, подписанным алгоритмом HS256 | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-02 | Токен имеет ограниченный срок действия (`exp`); значение по умолчанию — 60 минут, допустимый диапазон — 1…1440 минут | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-03 | Отсутствующий, повреждённый, просроченный токен или токен несуществующего пользователя приводит к ответу `401` с заголовком `WWW-Authenticate: Bearer` | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-04 | Деактивированная учётная запись не проходит аутентификацию: ответ `403 user-deactivated` | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-05 | Ответ на неверный пароль и на неизвестный email одинаков (`401 invalid-credentials`), чтобы не раскрывать факт регистрации адреса | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-06 | Пароли хранятся только в виде bcrypt-хэша с индивидуальной солью | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-07 | Пароль содержит не менее 8 символов, хотя бы одну букву и одну цифру | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-08 | Публичная самостоятельная регистрация отсутствует; учётные записи создаёт администратор. Первый администратор создаётся локальным скриптом `scripts/create_admin.py` | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-09 | Пароль первого администратора не передаётся аргументом командной строки | ОБЯЗАТЕЛЬНО |
| SEC-AUTH-10 | Механизм отзыва токенов (refresh/blacklist) | РЕКОМЕНДУЕТСЯ |

## 2. Авторизация

### 2.1. Роли (function-level)

| ID | Требование | Уровень |
|---|---|---|
| SEC-ROLE-01 | Роли: `admin`, `manager`, `worker`, `viewer`. Роль хранится в учётной записи и проверяется по данным хранилища, а не по полезной нагрузке токена | ОБЯЗАТЕЛЬНО |
| SEC-ROLE-02 | Проверка роли реализуется зависимостью `require_roles(...)`, возбуждающей `403 access-denied` | ОБЯЗАТЕЛЬНО |
| SEC-ROLE-03 | Матрица прав определяется таблицей ниже; операция, не указанная в таблице, доступна только `admin` | ОБЯЗАТЕЛЬНО |

| Операция | admin | manager | worker | viewer |
|---|---|---|---|---|
| Управление пользователями (`/users`) | да | — | — | — |
| Журнал действий (`/audit`) | да | — | — | — |
| Создание проекта | да | да | — | — |
| Изменение/удаление проекта, управление доступом | да | владелец | владелец | владелец |
| Чтение проекта и документов | да | по доступу | по доступу | по доступу |
| Создание/изменение/удаление документов | да | доступ `editor` | доступ `editor` | доступ `editor` |

### 2.2. Доступ к объектам (object-level)

| ID | Требование | Уровень |
|---|---|---|
| SEC-OBJ-01 | Каждая операция с `{project_id}` или `{document_id}` проверяет доступ пользователя к конкретному проекту до чтения или изменения данных (`app/core/permissions.py`) | ОБЯЗАТЕЛЬНО |
| SEC-OBJ-02 | Уровень доступа: `admin` и владелец — `editor`; прочие — по записи `ProjectAccess`; при отсутствии записи доступа нет | ОБЯЗАТЕЛЬНО |
| SEC-OBJ-03 | Если у пользователя нет доступа к проекту, ответ — `404` (существование чужого объекта не раскрывается). Если доступ на чтение есть, но не хватает уровня — `403` | ОБЯЗАТЕЛЬНО |
| SEC-OBJ-04 | Коллекции возвращают только объекты, доступные пользователю; значение `total` вычисляется с учётом того же фильтра | ОБЯЗАТЕЛЬНО |
| SEC-OBJ-05 | Поля, определяющие владельца, автора, статус при создании и выдавшего доступ (`owner_id`, `created_by`, `updated_by`, `granted_by`), заполняются сервером и не принимаются из тела запроса | ОБЯЗАТЕЛЬНО |
| SEC-OBJ-06 | Чувствительные действия (выдача и отзыв доступа, изменение роли и активности пользователя, удаление проекта, публикация и архивирование документа) записываются в журнал аудита | ОБЯЗАТЕЛЬНО |

## 3. Секреты и конфигурация

| ID | Требование | Уровень |
|---|---|---|
| SEC-CFG-01 | Секреты (`JWT_SECRET`, строка подключения к БД) передаются только через переменные окружения или файл `.env`, не попадающий в репозиторий | ОБЯЗАТЕЛЬНО |
| SEC-CFG-02 | При `ENVIRONMENT=production` запуск с демонстрационным `JWT_SECRET` или секретом короче 32 символов блокируется на этапе загрузки настроек | ОБЯЗАТЕЛЬНО |
| SEC-CFG-03 | При `ENVIRONMENT=production` запрещены `DEBUG=true` и символ `*` в `CORS_ORIGINS` | ОБЯЗАТЕЛЬНО |
| SEC-CFG-04 | CORS разрешает только origin из `CORS_ORIGINS`, методы `GET, POST, PUT, PATCH, DELETE, OPTIONS` и заголовки `Authorization, Content-Type` | ОБЯЗАТЕЛЬНО |
| SEC-CFG-05 | Каждый ответ содержит заголовки `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`; ответы API — `Cache-Control: no-store` | ОБЯЗАТЕЛЬНО |
| SEC-CFG-06 | Значение секрета не выводится в `repr` настроек, журналы и ответы API | ОБЯЗАТЕЛЬНО |
| SEC-CFG-07 | Публикация `/docs`, `/redoc`, `/openapi.json` управляется параметром `DOCS_ENABLED`. Для внутреннего API документация допускается во всех средах; при публикации во внешнюю сеть — отключается | ДОПУСКАЕТСЯ |
| SEC-CFG-08 | Необработанное исключение возвращает `500 internal-error` без трассировки, текста SQL и путей к файлам | ОБЯЗАТЕЛЬНО |
| SEC-CFG-09 | Файлы `.env`, `*.db`, журналы и каталоги IDE исключены через `.gitignore` | ОБЯЗАТЕЛЬНО |

## 4. Ресурсные ограничения и rate limiting

| ID | Требование | Уровень |
|---|---|---|
| SEC-RL-01 | Попытки входа ограничены скользящим окном по адресу клиента: по умолчанию 10 попыток за 60 секунд (`LOGIN_RATE_LIMIT`, `LOGIN_RATE_WINDOW_SECONDS`). Превышение — `429 rate-limit-exceeded` с заголовком `Retry-After` | ОБЯЗАТЕЛЬНО |
| SEC-RL-02 | Тело запроса больше `MAX_REQUEST_BODY_BYTES` (по умолчанию 1 МиБ) отклоняется кодом `413 payload-too-large` до разбора | ОБЯЗАТЕЛЬНО |
| SEC-RL-03 | Все коллекции пагинируются; `limit` ≤ 100, превышение отклоняется кодом `422` | ОБЯЗАТЕЛЬНО |
| SEC-RL-04 | Строковые поля имеют ограничения длины: название — 3…120, описание проекта — 2000, содержимое документа — 100 000 символов | ОБЯЗАТЕЛЬНО |
| SEC-RL-05 | Общий rate limiting для всех операций выполняется на уровне обратного прокси (nginx, API Gateway) при промышленной эксплуатации | РЕКОМЕНДУЕТСЯ |

**Решение о rate limiting (STD-SEC-09).** Внедрено ограничение частоты для
единственной публичной операции, подверженной перебору, — `POST /api/v1/auth/login`.
Ограничитель хранит состояние в памяти процесса, что достаточно для
развёртывания в одном процессе. При запуске нескольких реплик состояние
выносится во внешнее хранилище (Redis), а общий лимит для аутентифицированных
операций задаётся на обратном прокси (SEC-RL-05). Это зафиксировано как
остаточный риск в `CERTIFICATION_REPORT.md`.
